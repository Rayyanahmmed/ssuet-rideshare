Reading the numbers
-------------------
* Explore is the heaviest read: bounding-box filter + joins on driver/vehicle +
  a batched count of pending requests per ride. ~180 ms p50 with 20 concurrent
  clients on SQLite is acceptable for a university-sized user base (a few hundred
  daily journeys); PostgreSQL with the existing composite indexes is faster.
* Trip detail, My Trips and Notifications are comfortably sub-100 ms p50 because
  they are single-user, index-covered queries.
* No endpoint produced an error under concurrency — no 500s, no pool exhaustion.

If Explore ever becomes the bottleneck
--------------------------------------
1. Add a composite index on (status, direction, departure_at) — already present as
   `ix_rides_discovery`; verify with EXPLAIN ANALYZE on PostgreSQL.
2. Cache the first Explore page per (direction, area bucket) for ~30 s.
3. Move the `requests_count` sub-select into a denormalised counter updated on
   accept/reject if p99 matters more than write simplicity.
