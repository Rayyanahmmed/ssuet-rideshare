Load validation on the production stack — Phase 12
==================================================
Date: 2026-11-06
Stack: nginx 1.26 (TLS) → gunicorn 26.2 with 5 × UvicornWorker → PostgreSQL 17.11
Host: 2 vCPU sandbox (shared). Numbers vary ±20 % run to run on this host; treat them
as an order of magnitude, not a benchmark.

Dataset: 40 drivers, 400 open journeys, 1 passenger account (`scripts.load_check seed`).

------------------------------------------------------------------------------------------
1. Single-request latency (no concurrency) — what a student actually feels
------------------------------------------------------------------------------------------
Explore page (20 rides, 18.2 KB JSON, 4 SQL statements):  **11.6 – 13.0 ms**
Per-request SQL: 4 statements, 1.3 ms + 3 × 0.4 ms → the database is not the cost;
serialisation and framework overhead are.

------------------------------------------------------------------------------------------
2. Concurrency sweep — explore (default), 100 requests per level, direct to gunicorn
------------------------------------------------------------------------------------------
concurrency   rps      p50 ms   p95 ms   errors
          1    71.7      13.0     20.0        0
          5   142.2      31.0     62.7        0
         10   149.5      62.3    112.3        0
         20   145.0      98.1    224.3        0
         40   117.6     115.7    389.8        0

Throughput plateaus around **145–150 rps** for the heaviest endpoint while latency keeps
climbing: the workload is CPU-bound (JSON serialisation + validation) on a 2-vCPU host,
not database-bound. Adding workers past the core count adds queueing, not throughput —
measured directly: 2 workers → 97 rps / p50 185 ms, 5 workers → 105–145 rps / p50 98–128 ms
at concurrency 20.

------------------------------------------------------------------------------------------
4. Proxy overhead (nginx + TLS vs direct), concurrency 3
------------------------------------------------------------------------------------------
                   through nginx   direct    delta
explore (default)   p50 22.1 ms   p50 15.4 ms   ≈ +6.7 ms
explore (filtered)  p50 20.0 ms   p50 15.7 ms   ≈ +4.3 ms
explore (nearby)    p50 19.7 ms   p50 16.5 ms   ≈ +3.2 ms

The proxy costs **3–7 ms** per request (TLS + one extra hop) — worth it for one origin,
HSTS/CSP and the upload cap.

Sustained rates above 60 r/s from a single IP are refused by the edge limiter
(`limit_req zone=api_zone rate=60r/s`), which is why the throughput figures are measured
against the app directly. That was observed as 429s in the first through-nginx attempt —
the limiter doing its job, not a defect.

------------------------------------------------------------------------------------------
6. What this means for the pilot
------------------------------------------------------------------------------------------
* ~145 rps for Explore ≈ **8,700 requests/minute** — hundreds of concurrently browsing
  students on one 2-vCPU VPS. SSUET's realistic peak is far below that.
* If a single page ever needs to be faster, the win is in serialisation, not SQL:
  the page costs 2.5 ms in the database and ~10 ms in Python.
* Scale-out levers, in order: more vCPU (linear to ~4 cores), then a read replica for
  Explore, then caching `/rides` for 10 s. Not needed for a campus pilot.
